Mapa de Ruta del Proceso SDD
Las 5 Reglas No Negociables
1.
La IA nunca toma decisiones de producto sin preguntar (incluso si parecen triviales).
2.
La IA documenta toda decisión técnica por defecto en una sección explícita para validación.
3.
Leo la spec completa antes de aprobar. Prohibido "dar una mirada rápida".
4.
Toda spec pasa por pasada adversaria antes de aprobarse. Regla estricta, sin excepciones.
5.
Si una spec aprobada estaba mal: subo la versión y documento delta. Prohibido fix silencioso.

Flujo A · Ciclo Completo de Feature Nueva
Fase 1
Definir Necesidad
  • Redactar el problema en 1 o 2 líneas.
  • Notas crudas y dependencias estimadas.
  • Libre de formato estructural o formal.
Output: Notas internas crudas
Fase 2
Discovery de Feature
/sdd-discovery "<necesidad>"
  • IA hace preguntas numeradas por sección.
  • Resolver todos los [PENDIENTE] creados.
  • Validar decisiones técnicas por defecto.
Output: Cuestionario Discovery
Fase 3 Draft
Redacción de Spec
/sdd-spec "<discovery>" "<ID>"
  • Traduce discovery a spec sin cambiar producto.
  • Registrar en sdd/specs/<ID>.md.
  • Agregar fila con ID en Draft a INDEX.md.
Output: Feature Spec (Borrador)
Fase 4 Review
Pasada Adversaria
/sdd-adversarial-spec "<spec>" "<1|2>"
  • Corre en subagente con contexto limpio.
  • Cuestiona la spec buscando 10 clases de gaps.
  • Incorporar mejoras y subir versión. Máx 2 pasadas.
Output: Spec Iterada en Review
Fase 5 Approved
Aprobación y Verificación
/sdd-verify "<spec>"
  • Lectura completa en frío ➔ Estado Approved.
  • Gatillar verificación para evaluar bloqueo.
  • 🟢 Seguir · 🟡 Registrar desvío · 🔴 Freno.
Output: Spec Approved + Semáforo
Fase 6
Codegen por Capas
/sdd-codegen "<spec>" "<capa>"
  • Code por capas (1➔2➔3➔4). DB append-only.
  • Aprobar la tabla comparativa antes del código.
  • Correr /sdd-adversarial-code tras cada capa.
  • Gatillar /sdd-commit al verificar la feature.
Output: Código Aprobado + Commit

Flujo B · Modificar Feature Existente (Spec As-built)
0. Clasifico: Cambios funcionales sobre una feature activa van aquí. Bugs ➔ Flujo C. Nuevas independientes ➔ Flujo A.
1. Leer spec original completa: Identificar posibles desvíos o vacíos acumulados y completarlos como parte de esta modificación.
2. Discovery delta: Ejecutar /sdd-discovery acotado al cambio. Resolver pendientes y validar defaults.
3. Modifico Spec: /sdd-modify-spec "<spec>" "<delta>" edita de forma quirúrgica. Incrementa versión y agrega changelog.
4. Calidad: Pasada adversaria de spec ➔ Aprobación tras lectura reflexiva ➔ Semáforo de preparación con /sdd-verify.
5. Codegen delta: /sdd-codegen por capa afectada (Datos: migración append-only). Pasada adversaria de código y commit único.
Flujo D · Modelo de Ramas (Git Branching)
Regla de Ramas: Queda prohibido empujar directamente a main o staging. Todo cambio va por feature/*. Al deployar a prod, actualizo el estado de la spec en INDEX.md a Implemented y limpio ramas.
Flujo C · Gestión de Bugs
Clase de Bug Definición Procedimiento
Tipo A — Código El código no cumple lo que la spec dice. La spec es correcta. Corregir solo código (fix mínimo + test regresión).
Tipo B — Spec Spec con ambigüedades, omisiones o casos borde no contemplados. Actualizar primero la spec (vN+1), luego código.
Tipo C — Negocio El sistema cumple spec pero negocio cambió de parecer. No es bug. Reclasificar como feature (Flujo A o B).
Protocolo de Fix Mínimo (Regla de Cierre)
  • 1. Crear el archivo sdd/bugs/bugfix-NNN.md en estado Abierto.
  • 2. Regla de oro: Escribo el test de regresión ANTES de tocar código.
  • 3. Desarrollar el fix mínimo necesario (sin refactorizaciones de paso).
  • 4. Cerrar: Test verde + spec actualizada (si es B). Commit con prefijo fix(bugfix-NNN):
Zonas de Riesgo & Antipatrones
Zonas de Riesgo del Autor
  • Ansiedad: Apuro por avanzar y cerrar feedback sin reflexionar bien.
  • Cierre Prematuro: Aceptación superficial de hallazgos para "seguir".
  • Sub-especificar: Criterios de aceptación vagos y olvido de casos borde.
  • Evasión: "Es estándar/luego se ve" usado para no tomar decisiones hoy.
  • Cansancio: Trabajar de noche multiplica los desvíos procesales.
Antipatrones a Evitar
  • Vibe Coding: Escribir código sin una spec aprobada previa.
  • Spec Retroactiva: Escribir la spec después de haber codeado.
  • Saltear Adversaria: Omitir la pasada por ser "un cambio menor".
  • Codegen sin freno: Generar capas juntas sin validar tabla comparativa.
  • Fix Silencioso: Corregir un bug sin su bugfix-NNN.md ni test.
